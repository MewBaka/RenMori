# 威胁模型（在作出任何承诺之前先读这一篇）

English version: [threat-model.md](threat-model.md)

RenMori 对客户端保护能做什么、不能做什么保持诚实。本文档是本项目——及其营销——获准作出的宣称之基准。

## 无法回避的前提

Ren'Py 游戏在玩家的机器上运行。引擎要运行就必须读取自身的数据，因此：

- 解密逻辑随游戏一同下发
- 密钥材料可在客户端派生，因为别无它物能够解密
- 最终渲染的画面与解码后的音频存在于内存与屏幕之上

因此**没有任何客户端工具能使游戏不可破解。** 一名熟练而坚定的攻击者，只要拥有下发的二进制、一台调试器与足够的时间，终将从任意一款游戏中提取出任意单项数据。这就是白盒问题，历史上每一套本地 DRM 方案最终都败于它。任何声称相反者，都是在歪曲客户端保护的能力边界。

## RenMori 真正改变了什么

现实中的杠杆，按价值排序：

1. **击败现成工具**——`unrpa`、`rpatool`、`RenPack`、`RenpyEx` 与 `unrpyc`（含 `--try-harder` 与
   `un.rpyc` 注入）在受保护的构建上全部失效；这之所以重要，是因为现实中绝大多数数据提取与脚本泄露事件，不过是有人在运行其中某个工具，而仅会调用这些工具的 agent 也属同一类
2. **使破解不可迁移**——逐构建多态意味着逆向一款游戏只会得到仅适用于*该游戏、该版本*的工具，而非可复用的解包器，因此不存在可在论坛分享的"RenMori 解包器"
3. **使旧破解随时间失效**——每次发布都轮换方案，因此泄露或被逆向的旧构建对更新的构建毫无助益
4. **磁盘上无明文**——任何时刻都不存在任何以明文躺在文件系统上的文件，字体亦然

杠杆 1 的验证现状：`unrpa`、`unrpyc`（含 `--try-harder`）、`rpycdec` 与植入磁盘的脚本已由 [m1-results.zh-CN.md](m1-results.zh-CN.md) 与 [script-layer.zh-CN.md](script-layer.zh-CN.md) 中的记录覆盖。`rpatool`、`RenPack` 与 `RenpyEx` 尚未针对受保护的构建实际运行；它们读取的同样是 RPA 归档与 `.rpyc` 文件，而受保护的构建中磁盘上已不存在这些文件。

## RenMori 挡不住的攻击

请向客户如实陈述：

- **对所显示内容的屏幕录制与视频录制**——就定义而言无法阻止
- **熟练攻击者的内存提取**（例如针对运行中进程的 NinjaRipper 一类工具）——惰性分块解密会抬高成本，但不能阻止它
- **针对某一特定游戏、愿意投入时间的专家**——他们能够攻破那一款游戏、那一个版本，但无法把这次得手变成通用工具

真正阻止被注入的提取器将需要内核级反作弊，而这超出范围、对玩家不友好，并与性能优先及 Steam Deck/Proton 目标不相容。

## 本项目获准作出的宣称

> RenMori 使每一种标准的 Ren'Py 解包与反编译工具失效，磁盘上不留明文，并使每次构建各不相同，从而令通用解包器无从存在。它将提取的成本抬高到针对单一游戏、单一版本的专家级投入。它不能、也无法使游戏不可破解。

任何比这更强的说法都不可支撑，不得出现在文档、README 或营销之中。RenMori 许可证（`../LICENSE`）附有与之匹配的不提供担保与责任限制条款。
