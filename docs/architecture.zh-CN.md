# 架构

English version: [architecture.md](architecture.md)

RenMori 是一套**构建期工具**加**原生运行时核心**。它输入一个已经构建完成的
Ren'Py 8.x（Python 3）发行版构建，输出受保护的发行版构建。无需改动任何游戏源码。

原生启动器只是五个层级之一。其余四者——数据、脚本、引擎与逐构建多态——才是保护真正所在。

> **现状说明：** 本文档描述的是目标设计。已发行的开源基线在以下方面与之不同：运行时作为 Ren'Py 扩展（`game/renmori.rpe`）加载，而非经由原生启动器；脚本以 `.rpyc` 发行，其 pickle 载荷以独立密钥经 AES-GCM 加密，而非采用自定义 AST 格式；解密由 Python 参考读取器经 `ctypes` 调用平台的 AES 实现完成。逐构建多态、运行时密钥派生与原生启动器属于闭源插件。已交付并验证的内容参见 [m1-results.zh-CN.md](m1-results.zh-CN.md)、[script-layer.zh-CN.md](script-layer.zh-CN.md) 与 [m4.zh-CN.md](m4.zh-CN.md)。

## 全局首要原则：性能优先

任何与运行时性能冲突的保护手段都会被舍弃或削弱，绝不反向取舍。具体而言：

- **默认不使用任何重型加壳或虚拟化保护**（VMProtect、Themida 等）——它们拖慢启动，在
  Proton/Wine（Steam Deck 与 Linux）下失效，触发杀毒软件误报，并干扰 macOS 公证
- **热路径上不做任何反调试或自校验**——完整性校验仅在启动时进行一次
- **只使用对称、硬件加速的加密算法**（AES、AES-NI）——解密为原生实现（Rust 或 C），绝不使用
  Python 循环
- **多态是保护的承载者**，因为它是一次零运行时开销的构建期变换——策略是"无法批量破解"，而非
  "在运行时设防"
- **验收线**——受保护的构建在帧时间、场景切换与 CG、视频播放上与未受保护者无从分辨；若某项手段
  无法满足这一点，被舍弃的是该手段，而非性能

## 五个层级

### 1. 数据（含字体在内的每一个文件）

- `game/` 下的所有文件（图像、音频、视频、字体、`.rpyc`、`tl/`、JSON 等）均被封入一个
  **自定义加密容器**，完全取代 RPA 封包格式；每个文件拥有各自的密钥与完整性标签
- 运行时由一个原生模块接管 `renpy.loader` 的文件打开与索引入口，返回**已解密的流式**文件对象；字体
  （FreeType）、视频（ffmpeg）与音频均经由该加载器读取，因此单一咽喉点即可覆盖全部
  - **实现任务**——审计每一种资源类型的读取路径，确认其均经由 `renpy.loader`，并为任何绕过它的路径补上钩子
- **按偏移量进行的流式随机访问解密**，使视频与音频从不整体解密进内存；容器格式必须可按偏移寻址
- **解密结果复用 Ren'Py 既有的缓存**（纹理、音频），因此同一图像绝不会被解密两次

### 2. 脚本（源码混淆）

- 输出**并非**标准 `.rpyc`——而是采用自定义 AST 序列化，其类名映射、字段顺序与结构布局**逐构建随机化**，使依赖伪造
  `renpy` 模块的基于 pickle 的反编译器没有任何稳定目标可供绑定
- 脚本中内嵌的 Python（`init python`、`$`）在构建期编译并加密，仅在运行时解密以执行，调试元数据
  （源文件名、行号）可选剥除
- 对白与字符串以加密形式存储，仅在使用时打开

### 3. 引擎

- `renpy/` 引擎代码与 Python 标准库一并封包加密，并在启动时进行一次针对篡改的完整性校验
- **白名单加载**——仅加载构建期签名的脚本与模块，投放到游戏目录中的游离 `.rpy` 或 `.rpyc`
  文件一律拒绝，从而封堵 `un.rpyc` 式的注入反编译器
- 发行版构建禁用开发者控制台、开发者模式，以及导出数据的 CLI 子命令（`compile`、`dialogue`、`translate`、`add_from`、`merge_strings`）；`lint` 与 `run` 仍可使用

### 4. 原生启动器（外壳）

- 一个分平台的原生启动器取代 Ren'Py 自带者——它引导内嵌的 Python，从加密容器加载引擎，并
  **在运行时派生密钥**，磁盘上不留任何明文密钥
- 以 Rust 或 C 编写，编译为一个启动器与一个 CPython 扩展模块，因此核心逻辑位于原生代码而非 Python 之中

### 5. 逐构建多态（核心价值）

每次构建都会随机化容器格式参数、AST 编码映射与密钥派生路径，使通用解包器无从存在。这是一次构建期变换，不增加任何运行时开销。

## 开核拆分

准则：**任何公开的部分，即便被完全理解，也不得使任何人得以写出一个对所有 RenMori 游戏通用的解包器。**

### 开放（本仓库）

- CLI 骨架、配置解析、CI 集成，以及 GitHub Actions 示例
- **`renpy.loader` 加载器钩子框架与运行时 SDK**——接管加载器并将解密后的流回传给引擎的管道；将其作为开源发布本身即是一项*特性*，因为开发者可借此验证其中没有后门或回传，并自行调试兼容性
- **基线容器格式 v1 规范**——一种固定、公开、中等强度的格式
- 标准加密原语的使用方式——AES 是公开标准，公布其用法毫无代价
- 文档、样例与测试

开放部分可单独使用，处于基线强度（一种固定、可预测的格式）。

### 封闭（预编译二进制插件，已定）

- **多态 / 变异引擎**——每次构建如何随机化容器布局、字段顺序与 AST 类映射；它**仅在构建期运行，绝不下发给玩家**，因此一旦泄露便会暴露整个变换空间，使攻击者得以写出通用求解器，这正是它必须保持封闭的原因
- **密钥派生混淆**——密钥终究可在客户端派生，但*如何*派生与隐藏，才是抬高逆向成本之所在
- **原生反篡改与密钥恢复运行时**——以无源码的预编译二进制形式交付；它随游戏一同下发，因而终究可被逆向，封闭它只是抬高门槛

**交付方式：** 开放的 CLI 在构建期调用封闭的预编译二进制。它对 CI 友好、在预先放置插件后可离线运行，并契合免费分发。二者通过一套**稳定、有文档的进程接口**通信（经 stdin/stdout 的 CLI，或本地 IPC：输入为构建产物路径加配置，输出为受保护的产物加清单）。接口公开，实现不公开。每平台一个二进制。

可选地，运行时只接受由官方封闭二进制签名的构建指纹，使自行编写的弱多态层无法冒充它。

## 抗逆向（诚实的模型）

前提：一个下发给玩家、且必须在本地解密的二进制，无法被做到不可破解——这就是白盒问题。目标是抬高成本、使破解不可迁移，并轮换方案使旧破解随时间失效。成功意味着不存在通用解包器，且每款游戏都需要专门的专家级投入。完整论证见 [threat-model.md](threat-model.md)。

两件封闭产物，威胁模型各不相同：

1. **构建期二进制**（多态与密钥派生）——仅在开发或 CI 机器上运行，**绝不下发给玩家**，因此远更易于保护
2. **运行时核心**（随每款发行游戏一同下发的解密与反篡改模块）——在攻击者的机器上运行，且必须解密一切，因此是彻底的白盒

运行时核心的加固，按收益排序（并受*性能优先*约束）：

- **全原生，绝不用 Python**——关键逻辑的任何 `.py` 或 `.pyc` 都是破绽
- **多态带来不可迁移的破解**（最重要）——对一款游戏的完整逆向只会得到仅适用于该游戏、该版本的工具
- **密钥绝非静态常量**——而是在运行时由多个来源派生（代码段自哈希、散布的常量、计算所得值），使单次内存转储无法直接得到现成密钥；真正的白盒密码学既难又有学术构造已被攻破的先例，因此此处不作过度承诺
- **符号剥除、不含调试信息**的发行版构建
- **原生混淆**——控制流平坦化、不透明谓词与指令替换，经 obfuscator-LLVM（跨平台）实现，*仅在编译期进行，不带来任何运行时性能开销*
- **自完整性与解密绑定**——若二进制或引擎被打补丁，密钥派生会产出乱数而非干净的错误，使补丁更难诊断（仅限启动时）
- **反调试**——最小化并默认关闭，因为它是一场军备竞赛，误报会触发杀毒软件，且耗费性能
- **惰性分块解密，用后即释**——绝不在内存中整体保留一段 CG 或视频的明文，这会抬高内存提取的成本而不能阻止它

兼容性与性能结论（已由性能优先确定）：**原生代码、obfuscator-LLVM（轻量）、符号剥除与多态**。重型商业加壳仅作为 Windows 专属、默认关闭的选项，仅在实测确认无可感知性能影响时启用。

## 平台集成

### Steam

- **放行 Steam 覆盖层的注入**——覆盖层会注入游戏进程，激进的反篡改或反注入会将其拦下并破坏商店集成；性能优先已使反篡改保持最小化，此处明确放行该注入
- **不要与 Steam DRM 双重包裹**——Steam 的 DRM 会包裹并改写可执行文件，可能与启动时自校验冲突或将其触发，因此应测试兼容性，或建议客户跳过 Steam DRM，它本就薄弱
- 成就与云存档经由 Ren'Py 的 Python API，该 API 未被触动；`libsteam_api` 与 `steam_appid.txt` 仍可加载；加密容器为静态文件，因此 Steam 的文件校验与更新正常工作

### macOS 签名 / 公证（假定开发者*不*进行公证）

- **设计约束——只解密数据，绝不生成或执行解密后的代码**——这样便无需 hardened-runtime 权限，保护也不会迫使开发者走上付费签名之路，而未签名的发行版行为上与任何未签名的 Ren'Py macOS 游戏无异（Gatekeeper 右键打开）
- **Apple Silicon 至少需要一个临时（ad-hoc）签名才能运行**（`codesign -s -`，免费、无需账号）——构建工具默认对其产出的启动器与 dylib 进行临时签名
- 若开发者持有 Developer ID 并希望公证，这些二进制仍保持可重签名且与 hardened-runtime 兼容，并附有文档化的流程

## 许可

- 全部内容——框架与工具、封闭插件，以及随游戏内嵌下发的运行时——均依据 **RenMori License**
  （`../LICENSE`；中文 `../LICENSE.zh-CN.md`）：可免费用于保护任何 Ren'Py 游戏，包含商业作品，运行时亦可
  **以内嵌于发行游戏的形式再分发**且不收取任何费用，使开发者得以合法售卖其受保护的游戏
- 不被允许的是：售卖 RenMori 本身或其修改版，或以之运营付费加密服务——这是一份源码可得（source-available）的许可，而非 OSI 开源许可，因为无转售条款无法在宽松许可下表达
- 贡献须签署 **CLA**，使贡献的代码得以在单一、一致的许可下跨框架与封闭插件使用
- 第三方声明见 `../NOTICE`——**ffmpeg（LGPL/GPL）是首要的合规风险点**，此外还有 AES 库与 Ren'Py 自身的许可
- **安全免责声明**——声明没有任何保护是不可破解的，并在游戏被破解时限制责任
- **出口与加密声明**——含强加密的软件可能受出口管制约束
- **隐私声明**——无任何遥测（或一份诚实的清单），以消除对加载器钩子回传的任何疑虑

## 里程碑

- **M0**——本文档
- **M1**——数据层概念验证（目标平台为 Windows，在 macOS/arm64 上验证）：加密容器与加载器接管；图像、音频、视频与字体均可加载；`unrpa` 失效，磁盘上不再残留 `.rpyc` 或 `.rpy`；窗口化帧时间基准单独追踪，参见 [m1-results.zh-CN.md](m1-results.zh-CN.md)
- **M2**——脚本层与引擎层：以独立密钥加密脚本载荷、拒绝磁盘上的脚本，以及发行版锁定（自定义 AST 格式属于闭源插件），参见 [script-layer.zh-CN.md](script-layer.zh-CN.md)
- **M3**——单条命令的 CLI 与 CI：输入一个标准 Ren'Py 产物、一份配置文件、退出码、一份构建清单，以及一份 GitHub Actions 示例
- **M4**——逐构建多态；macOS（自动临时签名、可选公证）与 Linux/Steam Deck 启动器；验证 Steam 覆盖层、Steamworks 与 Proton/Steam Deck。开源基线交付了什么、哪些属于闭源或待硬件验证，参见 [m4.zh-CN.md](m4.zh-CN.md)

## 验证

以下为目标验收标准。当前结果记录于 [m1-results.zh-CN.md](m1-results.zh-CN.md)、[script-layer.zh-CN.md](script-layer.zh-CN.md) 与 [m4.zh-CN.md](m4.zh-CN.md)。

- **功能**——受保护的样例游戏在全部三个平台上运行并通关，每一项数据与全部剧情内容均正确
- **保护**——`unrpa`、`rpatool`、`RenPack`、`RenpyEx` 与 `unrpyc`（含 `--try-harder` 与 `un.rpyc` 注入）全部失效，且任何时刻磁盘上都不存在明文文件，字体亦然
- **性能**——CG 与视频密集的样例达到相对于未受保护构建的验收线
- **可用性与 CI**——在干净的 CI runner 上一条命令、正确的退出码，以及一条通过的示例工作流
