# M4 — polymorphism, launchers, platforms, Steam

M4 covers per-build divergence, cross-platform launch, and Steam. By our own
open-core split, the **polymorphism engine and the native launcher are the
closed component**, and Steam/Proton need their own hardware to
exercise. This document states precisely what the open baseline delivers and
verifies here, and what is closed or hardware-pending — no hand-waving.

## Per-build divergence (baseline, working)

"A break of one game doesn't port to the next" starts in the baseline: every
`protect` run produces a cryptographically independent build.

- A random 16-byte `container_id` salts all key derivation (HKDF), plus random
  per-file ids/keys and per-chunk nonces
- So the same game protected twice yields different `container_id`, different
  per-file keys, and a different container — one build's keys cannot read
  another's — proven in `tests/test_cli.py::test_two_builds_are_cryptographically_independent`
- The script key is independent of the container key (see
  [script-layer.md](script-layer.md))

What the baseline does **not** randomize: the container's byte layout and field
order, and the script AST class names are left standard (only re-encrypted).

### Closed upgrade: the polymorphism engine

The closed binary plugin randomizes the *structure* per build — container
layout and the compiled-script encoding — so no universal reader/decompiler can
be written even with keys in hand. It plugs into `renmori protect` over the
stable documented process interface ([architecture.md](architecture.md)); the
open CLI is the integration point. With no plugin available, the default
(full) strength fails rather than degrading; only `--strength auto` falls back to
the baseline. Mechanism and implementation are proprietary (private
`MewBaka/RenMori-core`).

## Launchers & platforms

The baseline loads through Ren'Py's **extension mechanism** (`game/renmori.rpe`),
which runs inside Ren'Py's own bundled Python during normal startup. It is
platform-agnostic: the same `.rpe` works on Windows, macOS, Linux, and Steam
Deck, because it relies only on Ren'Py's Python + `ctypes`, not on a per-OS
launcher binary.

AES-GCM backend per platform (one interface, `container/crypto.py`):

| Platform | Backend | Status |
|----------|---------|--------|
| macOS (arm64/x86_64) | OpenSSL EVP exported by `librenpython.dylib` | **verified here** (round-trip + in-engine on Ren'Py 8.5.2) |
| Linux / Steam Deck | OpenSSL EVP exported by `librenpython.so` | **verified** in-engine (CI, headless); same code path as macOS; Steam Deck run pending |
| Windows | OS CNG (`bcrypt.dll`), hardware AES | **verified** in-engine on Windows |

The library is found beside the Python executable
(`runtime_lib_candidates`, unit-tested), never via `CDLL(None)`.

### Native launcher (closed, opt-in)

The closed plugin ships a native per-platform launcher, on by default from 1.2.6
(`--no-launcher` opts out):

- **Boot attestation**: it holds a per-build launch share that the runtime folds
  into **runtime key derivation**, so the keys reconstruct only when the game is
  started through it, and an offline call into the shipped core derives the
  wrong keys
- **Boot-integrity check**: before starting the engine it refuses to launch when
  the distribution holds files Ren'Py would run from outside the container, such
  as a stray `.rpe` or a loose script; from 1.2.5 it also binds
  `game/renmori.rpe` and the scripts in `renpy/common` into the key
- **Installation**: it is installed as each platform's entry point, so launch
  options stay the same: inside the macOS `.app` (ad-hoc signed at build time,
  free, required on Apple Silicon, and re-signable with a Developer ID), as
  `<Name>.exe` on Windows, and as the engine stub `lib/py3-linux-x86_64/<Name>`
  that `<Name>.sh` starts on Linux; the original engine is kept beside it under a
  `.renmori_real` name
- **Verification**: built and unit-tested on all three platforms, verified
  in-engine on macOS

The **baseline ships no new executable**, so it adds no signing burden over the
original Ren'Py build.

## Steam

- **Overlay is safe without the launcher** — the Steam overlay injects a DLL
  into the game process, while RenMori (with `--no-launcher`) only hooks
  Ren'Py's *file loading*, never process/DLL injection or anti-tamper on the hot
  path, so it cannot block the overlay; with the native launcher (the default),
  the overlay and the Steamworks SDK are verified on macOS only, with Windows
  and Linux not yet tested
- **Files read outside `renpy.loader` stay on disk** — the Steam SDK reads
  `steam_appid.txt` directly (not through the loader), so it is kept unencrypted
  by default (`DEFAULT_KEEP_ON_DISK`); add any others via `keep_on_disk` in
  `renmori.toml`, as proven in `tests/test_cli.py::test_steam_appid_kept_on_disk`
- **Achievements / Cloud** go through Ren'Py's Python API, untouched; `.rmc` is a
  static file, so Steam's file verification and updates work normally
- **Don't double-wrap with Steam DRM** (it edits the executable and can conflict
  with a native launcher's self-check; it is weak anyway)

Full Steam/Proton/Steam Deck runs are pending that hardware; the properties
above are structural (hooks and file placement), not run-tested here.

For the developer-facing release flow (build → protect → SteamPipe upload, which
file goes to which depot, launch options), see
[steam-release.md](steam-release.md).

## Also in M4

- `renpy.exists()` (disk-only) now also consults the container, so games that
  probe with it see packed files (`_install_exists_fallback`)

## Honest status

Open baseline, verified on macOS/Ren'Py 8.5.2: per-build divergence, the
cross-platform `.rpe` path, Steam file-placement + overlay safety by
construction, `renpy.exists` fallback; the runtime is also verified in-engine on
Windows and Linux. Closed and shipped in the plugin: the polymorphism engine and
the native key-deriving launcher (verified in-engine on macOS, built and
unit-tested on Windows and Linux); pending hardware: live Steam and Steam Deck
runs.
