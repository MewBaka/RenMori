# M4——多态、启动器、平台与 Steam

M4 涵盖逐构建分化、跨平台启动与 Steam。按照本项目自身的开核拆分，**多态引擎与原生启动器属于闭源组件**，而 Steam/Proton 需要各自的硬件才能演练。本文档精确说明开源基线在此交付并验证了什么，以及什么是闭源或待硬件验证的——绝不含糊。

## 逐构建分化（基线，已可用）

「破解一款游戏无法迁移到下一款」始于基线：每一次 `protect` 运行都会产出一个在密码学上相互独立的构建。

- 一个随机的 16 字节 `container_id` 为全部密钥派生（HKDF）加盐，另有随机的逐文件 id/密钥与逐分块 nonce
- 因此同一款游戏保护两次会得到不同的 `container_id`、不同的逐文件密钥与不同的容器——一个构建的密钥无法读取另一个——已由 `tests/test_cli.py::test_two_builds_are_cryptographically_independent` 证明
- 脚本密钥独立于容器密钥（参见 [script-layer.md](script-layer.md)）

基线**不**随机化的部分：容器的字节布局与字段顺序，以及脚本 AST 的类名仍保持标准（仅重新加密）。

### 闭源升级：多态引擎

闭源二进制插件会逐构建随机化其*结构*——容器布局与编译脚本的编码——使得即便握有密钥，也无法编写通用读取器或反编译器。它通过稳定且有文档的进程接口（[architecture.md](architecture.md)）接入 `renmori protect`；开源 CLI 即集成点。无可用插件时，默认的完整保护强度会直接失败而不降级，仅 `--strength auto` 会回退到基线。其机制与实现为专有（私有仓库 `MewBaka/RenMori-core`）。

## 启动器与平台

基线通过 Ren'Py 的**扩展机制**（`game/renmori.rpe`）加载，它在正常启动期间运行于 Ren'Py 自身内置的 Python 内。它与平台无关：同一个 `.rpe` 可在 Windows、macOS、Linux 与 Steam Deck 上工作，因为它仅依赖 Ren'Py 的 Python 加 `ctypes`，而非逐操作系统的启动器二进制。

各平台 AES-GCM 后端（统一接口 `container/crypto.py`）：

| 平台 | 后端 | 状态 |
|------|------|------|
| macOS（arm64/x86_64） | 由 `librenpython.dylib` 导出的 OpenSSL EVP | **已在此验证**（往返 + 引擎内，基于 Ren'Py 8.5.2） |
| Linux / Steam Deck | 由 `librenpython.so` 导出的 OpenSSL EVP | **已验证**（引擎内，CI 无头）；与 macOS 同一代码路径；Steam Deck 运行待完成 |
| Windows | 系统 CNG（`bcrypt.dll`），硬件 AES | **已在 Windows 引擎内验证** |

该库在 Python 可执行文件旁查找（`runtime_lib_candidates`，有单元测试覆盖），绝不经由 `CDLL(None)`。

### 原生启动器（闭源，可选）

闭源插件随附分平台的原生启动器，自 1.2.6 起默认开启（`--no-launcher` 可关闭）：

- **启动认证**：它持有逐构建的启动份额，运行时将其纳入**运行时密钥派生**，因此只有经由它启动游戏时密钥才能还原，离线调用随附的原生核心只能派生出错误的密钥
- **启动完整性检查**：启动引擎前，若发行版中存在 Ren'Py 会从容器之外执行的文件（例如多余的 `.rpe` 或散装脚本），它会拒绝启动；自 1.2.5 起，它还把 `game/renmori.rpe` 与 `renpy/common` 中的脚本纳入密钥
- **装配方式**：装配为各平台的入口点，启动选项保持不变；在 macOS 上装配进 `.app`（构建时自动完成 ad-hoc 签名，免费，Apple Silicon 上必需，并保留以 Developer ID 重新签名的能力），在 Windows 上为 `<Name>.exe`，在 Linux 上为由 `<Name>.sh` 启动的引擎存根 `lib/py3-linux-x86_64/<Name>`；原引擎以 `.renmori_real` 名称保留在旁
- **验证情况**：已在三个平台上完成构建与单元测试，并已在 macOS 的引擎内验证

**基线不分发任何新的可执行文件**，因此与原始的 Ren'Py 构建相比，不会增加任何签名负担。

## Steam

- **不使用启动器时覆盖层（overlay）天然安全**——Steam 覆盖层向游戏进程注入一个 DLL，而 RenMori（以 `--no-launcher` 构建时）只钩住 Ren'Py 的*文件加载*，从不在热路径上做进程/DLL 注入或反篡改，因此无法阻断该覆盖层；使用原生启动器（默认）时，覆盖层与 Steamworks SDK 仅在 macOS 上验证，Windows 与 Linux 尚未测试
- **在 `renpy.loader` 之外读取的文件保留在磁盘上**——Steam SDK 直接读取 `steam_appid.txt`（不经加载器），故默认保持其未加密（`DEFAULT_KEEP_ON_DISK`）；其余文件可经 `renmori.toml` 中的 `keep_on_disk` 添加，已由 `tests/test_cli.py::test_steam_appid_kept_on_disk` 证明
- **成就 / 云存档**经 Ren'Py 的 Python API 进行，未受触碰；`.rmc` 是静态文件，因此 Steam 的文件校验与更新照常工作
- **不要与 Steam DRM 双重封装**（它会改写可执行文件，可能与原生启动器的自检冲突；且其本身就很薄弱）

完整的 Steam/Proton/Steam Deck 运行待相应硬件；上述属性是结构性的（钩子与文件放置），并非在此实机运行所得。

面向开发者的发布流程（构建 → 保护 → SteamPipe 上传、哪个文件进入哪个 depot、启动选项），参见 [steam-release.md](steam-release.md)。

## 诚实的状态

开源基线，已在 macOS/Ren'Py 8.5.2 上验证：逐构建分化、跨平台 `.rpe` 路径、Steam 文件放置与天然的覆盖层安全、`renpy.exists` 回退；运行时亦已在 Windows 与 Linux 的引擎内验证。闭源并已随插件发布：多态引擎与原生的密钥派生启动器（已在 macOS 的引擎内验证，已在 Windows 与 Linux 上完成构建与单元测试）；待硬件验证：Steam 与 Steam Deck 的实机运行。
